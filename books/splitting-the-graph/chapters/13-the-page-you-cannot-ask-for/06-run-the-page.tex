\section{Run the Page}
\label{sec:ch13-run-the-page}

\index{statement count!search page|(}%
The new root field asks the question \code{sessions} could not:

\begin{minted}{graphql}
query SearchPage($minimumScore: Float, $first: Int) {
  searchSessions(
    minimumScore: $minimumScore
    order: RATING_DESCENDING
    first: $first
  ) {
    nodes {
      session { id title }
      averageScore
      ratingCount
    }
    pageInfo { hasNextPage endCursor }
  }
}
\end{minted}

With \code{minimumScore} at 4.0 and \code{first} at 2, the router answers:

\begin{minted}[fontsize=\footnotesize]{json}
{
  "data": {
    "searchSessions": {
      "nodes": [
        {
          "session": {
            "id": "U2Vzc2lvbjoy",
            "title": "Reading a Query Plan"
          },
          "averageScore": 4.5,
          "ratingCount": 2
        },
        {
          "session": {
            "id": "U2Vzc2lvbjox",
            "title": "Schemas That Outlive Their Authors"
          },
          "averageScore": 4,
          "ratingCount": 3
        }
      ],
      "pageInfo": {
        "hasNextPage": false,
        "endCursor": "MQ=="
      }
    }
  }
}
\end{minted}

The first row is the 4.5 session at last. \code{hasNextPage} is the more
interesting field, because it is false about this ranking and this filter,
and not about the schedule that \code{sessions} happens to page.

\index{statement count!the cut is in one statement}%
The Search log says where the cut happened. Its one statement filters by
average score, orders by that column descending and then by session id, and
applies the limit, all inside the same \code{SELECT}; the tie-breaker is in
the statement with the limit and not in a repair step somewhere in the router.

\begin{center}
\begin{tabular}{@{}lr@{}}
\toprule
Service & SQL statements \\
\midrule
Search & 1 \\
Sessions & 1 \\
Ratings & 0 \\
Speakers & 0 \\
\bottomrule
\end{tabular}
\end{center}

Sessions spent its one statement on a batched entity lookup for the two chosen
keys, which is chapter~\ref{ch:router-n-plus-1}'s loader doing its job.
Ratings spent nothing, because the averages that ranked the page came out of
the Search projection and not out of the ratings table. Speakers spent nothing
because nobody asked for a speaker.

\index{query plan!the list owner goes first}%
The plan is a \code{Sequence} of two steps again, in the other order from
section~\ref{sec:ch13-cut-happens-first}: a \code{Single} fetch to Search,
subgraph~3, and then a \code{BatchEntity} fetch to Sessions, subgraph~0,
declaring that it waits for the first. Swap them and the opening of this
chapter comes back. The planner put them in the only order that answers the
request, because the list owner is now the service that holds the values.

\index{search document!the unrated session is still found}%
Drop the filter and the same field is a completeness check. In
rating-descending order the four averages come back as 4.5, 4.0, 3.0 and null,
so the session nobody rated is still there, last, with a count of zero, which
is the row a projection grouped out of the ratings table would have lost
without a word.

\subsection{The Consistency Bill}
\label{sec:ch13-consistency-bill}

\index{search projection!freshness|(}%
The seed is fixed, which is what lets this chapter measure the mechanism and
nothing else. A real system needs a path from a schedule change or a new
rating into the projection, and that path is a product decision: events,
change data capture off the two source tables, or a rebuild on a timer,
chosen by how stale the product can stand for discovery to be. Federation has
no opinion on it.

\index{search projection!staleness is a domain concern}%
The schema should say what that decision permits. If a rating submitted now
may take a minute to move a session up the ranking, write that down and watch
the lag. If a workflow needs to read its own write, an eventually updated
projection is the wrong thing to build it on. A search index is not a free
join; it is the same join moved to write time, and what it costs is that
staleness becomes a domain concern rather than a database one.

\index{cursor!stability is not the tie-breaker}%
Nor would I call the cursor stable because it has a tie-breaker. The
tie-breaker fixes the order of one snapshot, and if a score changes between
two requests a session can cross a cursor boundary in either direction.
Snapshot tokens and a versioned index are the features that would stop that,
and this chapter has built neither.

That is the whole trade. The graph gains a page it can answer honestly, and
one service takes on completeness, freshness and ordering as things it owns.
\index{search projection!freshness|)}%
