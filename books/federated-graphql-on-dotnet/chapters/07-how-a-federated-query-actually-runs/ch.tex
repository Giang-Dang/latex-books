\chapter{How a Federated Query Actually Runs}
\label{ch:how-a-federated-query-actually-runs}

Chapter~\ref{ch:the-federation-model} described a machine without ever starting
it. Entities, keys, directives, composition: all of it true, none of it running.
This chapter starts the machine and reads what comes out of it, message by
message, with the bodies printed in full.

To do that I need a federated graph, and Mosaic is not one yet. It becomes one
in chapter~\ref{ch:the-first-cut-extracting-catalog}, and spending that
extraction here would cost that chapter its subject. So this chapter runs on the
smallest arrangement that can show every message: two subgraphs sharing a single
entity, a router in front of them, three products and three reviews. It lives in
\code{samples/federated-wire/} in the companion repository, at tag \code{ch07},
and it exists for no other purpose than to be watched.

What makes it worth watching is that both subgraphs print everything. Every
request they receive and every response they send goes to the console, headers
and bodies included, through ASP.NET Core's own HTTP logging middleware rather
than through a proxy sitting in the middle. So the listings in this chapter are
not a reconstruction of what the router probably sent. They are what the server
process received, read from inside the server. Twice in what follows the
documentation and the running system disagree, and both times the console is
what I believed.
